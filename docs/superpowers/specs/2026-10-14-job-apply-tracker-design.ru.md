## Назначение

Django-приложение, в котором автор ведёт свои реальные отклики на вакансии.
Двойная цель, в порядке приоритета:

1. **Рабочий инструмент** — используется ежедневно начиная с первой
   MVP-версии, вместо разрозненного учёта в почте, на Profesia.sk и в
   markdown-отчётах.
2. **Портфолио** — демонстрирует уверенный, идиоматичный Django для найма на
   junior-позицию (в портфолио автора сейчас нет веб-проекта).

Проект одновременно **учебный**: автор осваивает Django по ходу разработки
(см. «Процесс разработки и обучения»).

### Боли, которые решаем (по приоритету)

1. **Забытые follow-up** — отклик уходит в тишину, и никто не напоминает
   компании о себе. Решение: блок дашборда «требует действия» — активные
   отклики без событий ≥ N дней (N — настройка пользователя, по умолчанию 7),
   вычисляется кастомным QuerySet-менеджером.
2. **Ручной перенос из job-ai-assist** — существующий ежедневный
   скрейпер/скорер автора ([job-ai-assist](https://github.com/OleksiiShcherbynin))
   выдаёт оценённые вакансии, которые сейчас копируются руками. Решение:
   push-API — job-ai-assist в конце ежедневного рана отправляет финалистов в
   трекер, они появляются во «входящих».
3. **Потеря материалов отклика** — какая версия CV куда ушла, что ответили,
   когда собеседование. Решение: лента событий по каждому отклику и
   файлы-вложения.

### Критерии успеха

- Начиная с конца этапа 1 автор заносит все новые отклики в трекер (и
  перестаёт терять follow-up).
- Репозиторий демонстрирует: кастомный User, CBV + ModelForm, свои
  QuerySet-менеджеры, тесты на N+1 (`assertNumQueries`), настроенную админку,
  DRF API с токен-аутентификацией и OpenAPI-схемой, Celery + Redis, HTMX,
  PostgreSQL, i18n en/sk, pytest + factory_boy + порог покрытия, security-CI,
  живой деплой с демо-аккаунтом.
- Django попадает в резюме только после того, как код опубликован.

## Граница систем

| Зона ответственности | job-ai-assist (существует) | job-apply-tracker (этот проект) |
|---|---|---|
| Скрейпинг Profesia.sk | да | никогда |
| Скоринг вакансий LLM-ом | да | никогда |
| Доставка ежедневных финалистов | пушит через API трекера (новый маленький коннектор, позже, **в репо job-ai-assist**) | принимает через `POST /api/v1/vacancies/` |
| Учёт откликов, статусов, событий, файлов | нет | да |
| Ручное занесение вакансий (отклики мимо Profesia) | нет | да |

Трекер никогда не читает SQLite или отчёты job-ai-assist. Единственная связь
между проектами — JSON-контракт push-эндпоинта.

## Пользователи и аутентификация

- **Multi-user с изоляцией данных**: каждая доменная запись принадлежит
  пользователю (FK), все запросы фильтруются по владельцу. Это архитектурно
  правильная форма и тема для разговора на собеседовании.
- **Без открытой регистрации**: аккаунты (авторский + демо) создаются
  management-командой / через админку. Login/logout — встроенные вьюхи Django
  со своими шаблонами. Подтверждение email и сброс пароля — вне скоупа.
- **Кастомный User** (`accounts.User`, наследник `AbstractUser`) с первого
  дня, до первой миграции. Несёт пользовательские настройки, например
  `follow_up_days` (по умолчанию 7).

## Структура проекта

Три Django-приложения по доменам (канонический слоёный Django — сознательно
НЕ ports & adapters: цель — идиоматичный Django):

```
job-apply-tracker/
├── config/              # settings, корневые urls, wsgi/asgi
│   └── settings/        # base.py / dev.py / prod.py
├── accounts/            # кастомный User
├── tracker/             # домен: модели, менеджеры, views, формы, шаблоны
├── api/                 # DRF (появляется на этапе 2)
├── manage.py
└── docker-compose.yml   # PostgreSQL (+ Redis на этапе 3)
```

## Модель данных

У всех доменных моделей есть `owner = FK(User)` и таймстемпы
создания/обновления.

- **Company** — `name`, `website`, `notes`. Имя уникально в пределах
  владельца.
- **Vacancy** — `company FK`, `title`, `url`, `source`
  (`manual` / `job_ai_assist`), `external_id` (ID оффера Profesia, для
  идемпотентных пушей; nullable, уникален в пределах владельца, когда задан),
  `score` + `score_reasons` (от job-ai-assist; у ручных пусто), `salary`
  (текст, как есть), `location`, `state`: `inbox` → `applied` / `dismissed`
  (при отклонении сохраняется причина — пригодится для статистики «сколько
  входящих я отсеял»).
- **Application** — `OneToOneField(Vacancy)`. Один отклик на вакансию:
  соответствует реальности и упрощает формы; повторный отклик через месяцы —
  это новая вакансия (её создаст новый пуш). `status`: `applied` → `replied`
  → `interview` → терминальные `offer` / `rejected` / `no_response` /
  `withdrawn`. Поля: `applied_at`, `notes`.
- **ApplicationEvent** — `application FK`, `type` (`status_change`, `note`,
  `call`, `interview`, `email`), `happened_at`, `text`. Смена статуса
  Application автоматически пишет событие `status_change` (метод модели, не
  сигналы).
- **Attachment** — `application FK`, `FileField`, `label` (например
  «CV v3 EN»), `uploaded_at`. Хранится на локальном media-томе;
  валидация типа/размера файла — в форме.

**«Требует действия»** вычисляется, а не денормализуется: отклики в активных
статусах (`applied`, `replied`), у которых последнее событие старше
`follow_up_days` владельца, через `annotate(Max("events__happened_at"))` в
кастомном QuerySet. Списочные вьюхи покрыты тестами `assertNumQueries`,
чтобы ловить N+1.

## Экраны (серверные Django-шаблоны; без JS-сборки; HTMX на этапе 3)

- **Дашборд** — список «требует действия», счётчики по статусам, последние
  события.
- **Входящие** — вакансии в состоянии `inbox`, отсортированы по score по
  убыванию; действия: «Откликнулся» (создаёт Application; спрашивает дату /
  вложения) и «Отклонить» (с причиной).
- **Список откликов** — фильтр по статусу/компании, поиск.
- **Деталь отклика** — статус (смена через форму с комментарием → пишется
  событие), лента событий, вложения, заметки.
- **CRUD компаний/вакансий** — ручное занесение откликов мимо Profesia.
- **Админка** — настроенные `list_display`, фильтры, поиск, инлайн событий в
  отклике; служебный вход автора и витринная фича.
- **Auth** — login/logout.

Стилизация: лёгкий/classless CSS-фреймворк (Pico.css или Bootstrap), выбор —
на этапе реализации; это не дизайн-проект.

## API (этап 2)

- `POST /api/v1/vacancies/` — bulk-создание/обновление вакансий, которые
  пушит job-ai-assist. Идемпотентно по (`owner`, `external_id`): повторный
  пуш того же оффера обновляет, а не дублирует. Company создаётся по имени,
  если её ещё нет.
- DRF TokenAuth (токен на пользователя, выдаётся management-командой),
  throttling, drf-spectacular со Swagger UI на `/api/schema/swagger-ui/`.
- Коннектор-отправщик — отдельная задача в репо job-ai-assist, вне скоупа
  здесь, кроме JSON-контракта, который зафиксируем на этапе 2.

## Этапы

- **Этап 0 — каркас**: git-репозиторий, Django 5.2 LTS, разделённые
  настройки, кастомный User (до первой миграции), PostgreSQL через
  docker-compose, pytest-django + factory_boy + порог покрытия,
  GitHub Actions: ruff, pytest, coverage-гейт, bandit, pip-audit, gitleaks
  (та же планка безопасности, что в job-ai-assist). Ветки + PR, маленькие
  коммиты, TDD с самого начала.
- **Этап 1 — MVP** (после него автор начинает ежедневно пользоваться):
  модели + миграции + админка → auth → CRUD компаний/вакансий → входящие →
  отклики + события + вложения → дашборд «требует действия».
- **Этап 2 — API для job-ai-assist**: DRF-эндпоинт как выше; затем коннектор
  в репо job-ai-assist (отдельный проект, отдельный план).
- **Этап 3 — витринные фичи**: HTMX (смена статуса и добавление события без
  перезагрузки), Celery + Redis (утренний email-дайджест «требует действия»),
  i18n en/sk.
- **Этап 4 — деплой**: живой инстанс + демо-аккаунт с сид-данными
  (management-команда), README со скриншотами, security-заголовки/HTTPS.
  Хостинг выбирается на этапе 4 (кандидаты: Fly.io, Railway, Hetzner).

Каждый этап едет через feature-ветки и PR с зелёным CI.

## Тестирование

- pytest-django + factory_boy; порог покрытия в CI (точный процент задаётся
  на этапе 0, цель ≥ 85–90%).
- TDD для доменной логики (методы моделей, менеджеры, формы, вьюхи).
- `assertNumQueries` на каждой списочной вьюхе (дашборд, входящие, отклики).
- На этапе 2 — API-тесты на идемпотентность, аутентификацию и валидацию.

## Процесс разработки и обучения

Автор учит Django через этот проект:

- Перед каждым блоком ментор (Claude) объясняет концепцию (что такое
  миграция, как диспатчится CBV, что делает `get_queryset`, …).
- **Бо́льшую часть кода пишет Claude с объяснениями.** Ключевые вещи каждого
  блока (первая модель, кастомный менеджер, первая CBV, первая форма, первый
  DRF-сериализатор, …) автор после объяснения пишет сам; Claude помогает,
  когда застрял, и ревьюит.
- Маленькие коммиты; в сообщении коммита — «почему».

## Вне скоупа (YAGNI)

- Открытая регистрация, подтверждение email, сброс пароля.
- Любой скрейпинг или скоринг в этом проекте.
- Несколько откликов на одну вакансию.
- Уведомления сверх email-дайджеста этапа 3 (никакого Telegram здесь — у
  job-ai-assist свой бот).
- Kanban с drag-and-drop, графики/аналитика (блока счётчиков пока
  достаточно).
- S3/объектное хранилище для media (локального тома на этом масштабе
  хватает).
