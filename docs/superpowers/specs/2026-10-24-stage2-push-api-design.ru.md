# Этап 2 — job-ai-assist отправляет вакансии в трекер

Дата: 2026-10-24
Статус: проверен агентом-разработчиком, ждёт одобрения автора
Опирается на: [дизайн MVP](2026-10-14-job-apply-tracker-design.ru.md), [архитектуру как построено](../../architecture.ru.md)

> Это перевод [английского документа](2026-10-24-stage2-push-api-design.md) для удобства автора.
> При расхождениях главный — английский файл.

## Зачем

Каждое утро job-ai-assist (авторский скрейпер + LLM-оценщик вакансий с Profesia.sk) выдаёт
оценённые вакансии и присылает отчёт в Telegram. Автор читает вакансии с оценкой 40+, открывает,
решает — и сейчас вынужден перепечатывать интересные в трекер руками. Этап 2 убирает
перепечатывание: job-ai-assist отправляет каждую оценённую вакансию в трекер, «Входящие» показывают
то, что стоит посмотреть, а автору остаётся только решать.

Заодно появляется то, что уже просит ежедневное использование: «Входящие», которые не захламляются,
архив закрытых откликов и защита от повторного отклика на ту же перевыложенную вакансию.

## Цели

1. job-ai-assist сам доставляет в трекер каждую **оценённую** вакансию (с любым баллом) после
   ежедневного рана, без участия автора.
2. «Входящие» по умолчанию показывают только то, что заслуживает внимания сегодня; всё остальное —
   в одном переключателе.
3. Закрытые отклики уходят с глаз в архив, но полностью доступны по запросу.
4. Повторный отклик на перевыложенную вакансию — осознанное решение, видимое на обеих попытках.
5. Трекер постоянно работает на ноутбуке рядом с job-ai-assist, `runserver` не нужен.
6. Портфолио: настоящий REST API с токен-аутентификацией и OpenAPI-схемой, идемпотентный пакетный
   приём, тесты.

## Не цели

- Забирать данные из job-ai-assist (pull), вебхуки, любые другие источники вакансий.
- Правка или удаление данных трекера через API (только приём).
- Выкладка в интернет (этап 4), фоновые задачи и e-mail дайджесты (этап 3).
- Статистика отказов по компаниям (автор явно отказался: у одной компании много разных вакансий, и
  пометка «эта компания тебе отказывала» на уровне компании вводила бы в заблуждение).

## Анти-цели (провал, даже если «работает»)

- Отправка перетирает решение автора (отклонённая или откликнутая вакансия снова появляется во
  «Входящих», меняется состояние или заметки).
- Один и тот же оффер появляется во «Входящих» дважды.
- Недоступность трекера ломает или задерживает утренний отчёт в Telegram.
- Токен API попадает в git, логи или командную строку (аудит-хук на машине логирует каждую команду).

## Ограничения

- Два отдельных репозитория и два отдельных контейнера в одном Docker Desktop. Единственная связь —
  JSON-контракт ниже. Каждый репозиторий по-прежнему запускается сам по себе.
- Трекер сохраняет существующие данные PostgreSQL (том `pgdata` текущего compose).
- job-ai-assist построен как ports & adapters (чистое `core/`, адаптеры в `local_connectors/`,
  сборка в `app/`); его коннектор следует этому стилю. Трекер остаётся слоёным Django.
- Всё из MVP остаётся в силе: изоляция владельцев, POST/redirect/GET, бюджеты запросов в тестах,
  порог покрытия, security-CI.
- Формат работы: весь код пишет Claude; перед блоками — короткие уроки (выбор автора).

## Часть A — трекер (этот репозиторий)

### A1. API приёма

- Новое приложение `api/`. Django REST Framework, `rest_framework.authtoken`, drf-spectacular.
- `POST /api/v1/vacancies/` — аутентификация заголовком `Authorization: Token <ключ>`; всё
  создаётся для `request.user`. Без токена или с неверным токеном → 401.
- Токен на пользователя, создаётся management-командой (`create_api_token <username>`, печатает
  ключ один раз) или в админке. Автор сам кладёт его в `.env` job-ai-assist.
- Throttling: лимит на пользователя с запасом на один дневной пакет плюс повторы (точное число —
  на усмотрение исполнителя; job-ai-assist шлёт несколько запросов в день).
- OpenAPI-схема на `/api/schema/` и Swagger UI на `/api/schema/swagger-ui/`; в схеме нет данных,
  она может быть публичной.

**Запрос** — пакет, максимум 200 элементов:

```json
{
  "vacancies": [
    {
      "external_id": "O5350242",
      "title": "Junior Python Developer",
      "company": "Softec",
      "url": "https://www.profesia.sk/praca/softec/O5350242",
      "location": "Bratislava",
      "salary": "1 800 - 2 200 EUR/month",
      "score": 78,
      "score_stage": "final",
      "reasons_en": ["Python and Django match", "Junior-friendly"],
      "reasons_ru": ["Совпадает стек Python и Django", "Подходит джуниору"],
      "first_seen_at": "2026-10-20T08:14:03+00:00"
    }
  ]
}
```

| Поле | Правило |
|---|---|
| `external_id` | обязательное, ≤ 50 символов; ID оффера Profesia |
| `title` | обязательное, ≤ 255 |
| `company` | необязательное; нет или пусто → компания `Unknown company` |
| `url` | обязательное, корректный URL |
| `location`, `salary` | необязательный текст, как на Profesia |
| `score` | обязательное, целое 0–100 |
| `score_stage` | обязательное, `rough` или `final` |
| `reasons_en`, `reasons_ru` | необязательные списки строк |
| `first_seen_at` | необязательное, ISO 8601 с часовым поясом; когда job-ai-assist впервые увидел оффер |

**Ответ** — `200`, по одному результату на элемент, в порядке запроса:

```json
{"results": [
  {"external_id": "O5350242", "status": "created", "id": 41},
  {"external_id": "O5349001", "status": "updated", "id": 17},
  {"external_id": "", "status": "invalid", "errors": {"external_id": ["This field may not be blank."]}}
]}
```

Элементы независимы: невалидный элемент не блокирует валидные (иначе одна плохая запись навсегда
застряла бы в очереди повторной отправки). Повреждённое тело (не JSON, нет списка `vacancies`,
больше 200 элементов) — `400` для всего запроса.

**Правила приёма** (всё в пределах данных пользователя запроса):

- **Новый `external_id`, и у владельца есть вакансия без `external_id` с тем же отпечатком**
  (занесённая руками до этапа 2) → **усыновить** её: проставить `external_id` и заполнить поля от
  job-ai-assist (оценка, этап, причины, `first_seen_at`, а location / salary — только если пустые).
  Её состояние, отклик, заметки, компания и `source` не меняются. Одна строка, без дубля. Если
  подходит несколько ручных — усыновить самую свежую.
- **Новый `external_id`, усыновлять нечего** → новая `Vacancy` с `source=job_ai_assist`,
  `state=inbox`. Компания ищется по имени без учёта регистра и создаётся, если её нет.
- **Известный `external_id`** → обновить только то, что принадлежит job-ai-assist: название, url,
  город, зарплату, оценку, этап оценки, причины (причины — только если присланы). Никогда не трогать
  `state`, `dismiss_reason`, привязку к компании и отклик. Ни дубля, ни возвращения во «Входящие».
- `first_seen_at` записывается один раз (при создании) и последующими отправками не сдвигается.
- Каждый элемент сохраняется атомарно; весь пакет целиком — не обязательно.

### A2. Дополнения модели Vacancy

- `score_stage` (`rough` / `final`, пусто у ручных вакансий).
- Причины оценки на английском и русском хранятся отдельно (существующее `score_reasons` становится
  английским или заменяется — на усмотрение исполнителя, с миграцией данных при переименовании).
- `first_seen_at` (может быть пустым); **возраст** вакансии = `first_seen_at`, если задан, иначе
  `created_at`. Важно для первой отправки: накопленный архив уже виденных офферов должен лечь как
  старый, а не как свежий на 5 дней.
- Лимиты длины текста достаточные, чтобы реальные данные Profesia не становились `invalid`
  (исполнитель сверяет длины `url`, `salary`, `location` с тем, что хранит job-ai-assist).
- Нормализованный **отпечаток** компании + названия (нижний регистр, без диакритики, схлопнутые
  пробелы — то же правило, что у job-ai-assist для перепостов), хранится с индексом, считается при
  сохранении, для ручных и присланных вакансий одинаково.

### A3. «Входящие»: что видно по умолчанию и два переключателя

Новые настройки пользователя рядом с `follow_up_days` (правятся в админке):
`inbox_min_score` (по умолчанию **40**) и `inbox_fresh_days` (по умолчанию **5**).

Каждая вакансия без отклика попадает ровно в один вид:

- **«Входящие» по умолчанию** — состояние `inbox`, оценка ≥ `inbox_min_score` **или оценки нет**
  (ручные), возраст ≤ `inbox_fresh_days`, и это **самая новая** вакансия своего отпечатка среди
  нерешённых (если компания перевыложила вакансию, пока оригинал не решён, видна только перевыложенная;
  старая уходит в «Неразобранные» с пометкой «во Входящих есть более новая версия»). Сортировка по
  оценке, как сейчас.
- **Переключатель «Неразобранные»** — оценка ≥ `inbox_min_score` или нет оценки, и при этом либо
  всё ещё `inbox`, но старше окна свежести (или скрыта более новым перепостом), либо `dismissed`
  (показывается с причиной). Ручные вакансии стареют так же, как присланные.
- **Переключатель «Оценка ниже 40»** — оценка < `inbox_min_score`, состояние `inbox` или
  `dismissed`, любой возраст.
- Переключатели — GET-параметры (можно сохранить в закладки), их можно сочетать.
- У карточек во всех видах есть **«I applied»**; у отклонённых ещё **«Back to inbox»** (только POST,
  снимает отклонение и больше ничего не сбрасывает).
- На каждой карточке: оценка с маленькой пометкой «rough» при `score_stage=rough`; русские причины,
  если есть, иначе английские.
- Счётчик «Входящих» на дашборде считает только вид по умолчанию.

### A4. Архив откликов

- Статусы **Rejected, No response, Withdrawn** — «закрытые». Список откликов по умолчанию их
  скрывает; переключатель **«Архив»** их показывает. Ничего не удаляется.
- Offer остаётся видимым (это результат, его незачем прятать). «Требует действия» не меняется
  (закрытые статусы он и так не учитывает).

### A5. Перепосты и повторные отклики

«Та же вакансия» = тот же владелец, тот же отпечаток, другая строка вакансии (работает и для
присланных, и для ручных, поэтому первая отправка свяжется и с откликами, занесёнными руками).

- **Карточка во «Входящих»** вакансии, чей отпечаток совпадает с вакансией, на которую автор
  **откликался**: пометка «Already applied on DATE — STATUS» со ссылкой на тот отклик. Если совпавшая
  была **отклонена**: пометка «Dismissed before: REASON».
- **«I applied» на такой вакансии** показывает предупреждение с прошлыми попытками и требует явного
  подтверждения (например, галочка «Yes, apply again») перед созданием отклика.
- Новый отклик хранит **прошлую попытку** (ссылку на более ранний отклик с тем же отпечатком, самый
  свежий из них). Обе страницы откликов показывают ссылку (новее ↔ раньше).
- Если ранний отклик ещё активен — оба остаются активными и помечены как связанные. Если закрыт — он
  уже в архиве (A4), и автор работает с новым.
- Один отклик на строку вакансии остаётся (OneToOne); повторный живёт на новой строке вакансии.

### A6. Трекер постоянно работает в Docker

- `Dockerfile` для веб-приложения (Python 3.12 slim, не-root пользователь, gunicorn, статика через
  WhiteNoise) и сервис `web` в существующем `docker-compose.yml` рядом с `db`, с
  `restart: unless-stopped`. При старте применяет миграции.
- **Рабочие данные и данные разработки разделены.** Контейнер владеет существующей базой `tracker`
  (реальные данные автора остаются на месте). Разработка (`runserver`, `migrate` из feature-ветки,
  тесты) переходит на свою базу `tracker_dev` на том же сервере Postgres, поэтому работа в ветке
  никогда не мигрирует и не засоряет рабочие данные.
- Загруженные файлы рабочего приложения лежат в именованном томе; файлы, уже лежащие в `media/` на
  хосте, один раз копируются туда при настройке. Разработка продолжает использовать `./media`. Media
  остаются приватными (отдаются только через `attachment_download`).
- Настройки в стиле продакшена из переменных окружения, флаги «только HTTPS» отключаемы для этого
  локального HTTP. Секреты (секретный ключ Django) — из `.env`, который не попадает в git.
- Браузер открывает его на `http://localhost:8000`. job-ai-assist достучится до него через **общую
  сеть Docker** с фиксированным именем, которую объявляют **оба** compose-файла (не `external`):
  кто стартует первым, тот её и создаёт, и job-ai-assist запускается, даже если трекер ни разу не
  поднимали; хост — имя веб-сервиса. *(Это заменяет идею с `host.docker.internal` из обсуждения:
  общая сеть не зависит от того, как Docker Desktop маршрутизирует запросы к хосту.)* Адрес —
  настройка на стороне job-ai-assist.
- `runserver` остаётся только для разработки.

## Часть B — отправщик в job-ai-assist (его репозиторий, после части A)

- Адаптер в `local_connectors/`, который отправляет пакеты в трекер; порт в `core/ports.py`, если
  так в репозитории описываются внешние системы.
- Очередь отправки (outbox) в существующем SQLite-хранилище по образцу таблицы `deliveries`
  (Telegram): каждая оценённая вакансия (статусы `scored-rough`, `scored-final`, `repost-of-*`)
  ставится в очередь с текущими данными; принятые (`created` / `updated`) помечаются доставленными;
  `invalid` логируются и не повторяются; при ошибках связи элементы остаются в очереди.
- Переоценка (rough → final) ставит вакансию в очередь заново, чтобы трекер получил новую оценку.
- Отправка — после ежедневного рана и при каждой 15-минутной проверке, пока в очереди что-то есть.
  Недоступность трекера никогда не роняет ран и не задерживает отчёт в Telegram.
- При первом подключении весь архив уже оценённых вакансий ставится в очередь один раз (с
  `first_seen_at`, чтобы лечь как старые).
- Настройки: адрес трекера и токен из `.env` (автор правит `.env` сам; токен никогда не печатается,
  не логируется и не передаётся в командной строке). Без них отправщик просто выключен.
- Его compose объявляет ту же сеть с фиксированным именем (см. A6); он должен запускаться и работать
  нормально, когда трекера нет.
- `score_stage` для `repost-of-*` берётся из статуса оригинала (`scored-final` → `final`).
- Тесты с поддельным HTTP-эндпоинтом; без сети в тестах (правило репозитория).

## Тестирование

- Часть A: тесты API — аутентификация (401), создание, идемпотентная повторная отправка, никакого
  возврата отклонённых / откликнутых, переиспользование компании без учёта регистра,
  `Unknown company`, усыновление подходящей ручной вакансии (без дубля, решения сохранены), результаты
  `invalid` по элементам, 400 для повреждённого тела и > 200 элементов, `first_seen_at` сохраняется
  при обновлении; тесты «Входящих» по умолчанию / переключателей / возраста / порога; каждая вакансия
  без отклика ровно в одном виде; во «Входящих» по умолчанию только самый новый нерешённый перепост;
  «Back to inbox»; переключатель архива; пометки перепостов, обязательное подтверждение, ссылка на
  прошлую попытку; число запросов на «Входящих» и списке откликов остаётся фиксированным. Порог
  покрытия прежний.
- Docker: ручной чек-лист (контейнер поднят, вход, рабочие данные на месте, разработка работает на
  `tracker_dev`, API доступен из другого контейнера в общей сети, job-ai-assist стартует при
  выключенном трекере).
- Часть B: тесты в наборе job-ai-assist, в его стиле.

## На усмотрение исполнителя

Точный лимит throttling; имена полей в моделях трекера; как называется модуль настроек для Docker
и как переключаются HTTPS-флаги; структура сериализаторов / views в `api/`; разметка пометок и
переключателей; подтверждение — галочкой или вторым шагом; форма таблицы очереди в job-ai-assist.

## Порядок

Сначала часть A в этом репозитории (API можно проверить через curl и Swagger ещё до отправщика),
потом часть B в job-ai-assist. У каждой части свой план, своя ветка и свой PR.
